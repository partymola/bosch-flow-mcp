`CLAUDE.md` symlinks to this file. It orients AI agents and contributors working *in* the code, and deliberately does not repeat the user-facing docs:

- **What it is, install, auth, sync, tools, config, usage** -> [README.md](README.md)

**This is a public open-source repository.** Read the Data Safety Rules before committing.

## Data Safety Rules

The `scripts/check-no-data.sh` pre-commit hook refuses `*.db` files with their journals and copies, `*.bak` and `*.backup` files, anything under the top-level `config/` except `.gitkeep` and paths ending in `.example` or containing `.example.`, any added, changed or renamed file over 100KB except the root `uv.lock`, and any path containing a newline. Install it per [CONTRIBUTING.md](CONTRIBUTING.md#install-the-pre-commit-hook); CI does not run it. **It matches paths and sizes and never reads contents**, so a secret in code passes, and so does a credential file outside `config/` or named like an example. None of the rules below is fully enforced by it; check them yourself:

1. `config/bosch_tokens.json` and `bosch_flow.db` must stay gitignored - verify `git status` shows no token/db files
2. Test fixtures (`tests/conftest.py`) use fictional UUIDs (`00000000-0000-0000-0000-000000000001`) and round numbers only - no real bike data ever enters tests
3. `config/bosch_config.example.json` (committed) holds only the public EUDA client ID and blank fields - confirm no real credentials

## Architecture

- **Entry point**: `src/bosch_flow_mcp/cli.py` - routes `auth`/`sync` subcommands or starts the MCP stdio server
- **MCP server**: `mcp_instance.py` creates the shared `MCPServer` instance
- **Auth**: `auth.py` - two flows. The default `one-bike-app` PKCE flow (iOS deep-link redirect, DevTools copy-paste). If `config/bosch_config.json` holds a EUDA `client_id`, auth switches to the EUDA flow (plain `localhost:4200` callback). `token_is_euda()` reads the token file fresh each call, so routing follows the current sign-in without a restart. **The EUDA flow's listener is `_CallbackServer`, not a bare `HTTPServer`, and that matters on Windows.** `HTTPServer` sets `allow_reuse_address`, which on POSIX only waives TIME_WAIT. On Windows it is consent to be displaced: per Microsoft's same-user table for a specific-address bind, a first socket holding the address with `SO_REUSEADDR` is bound over by a second one asking for the same, so another process could take the authorisation code. **Not asking is what closes it** - the same table shows a first bind with neither option refusing that second bind. `SO_EXCLUSIVEADDRUSE` is asked for as well because Microsoft recommends it for server sockets and because it is the half that would still hold for a wildcard bind, which this listener is not. Never ask for both: reuse requested after exclusive use is the configuration Microsoft calls insecure, and `allow_reuse_port` (the POSIX-side equivalent hazard) is pinned off for the same reason. The cost is that a Windows port stays held until the previous connection finishes closing, normally a couple of minutes. `_setup_euda_auth` catches the resulting `OSError` and binds before opening the browser. `TestTheCallbackPortIsNotShared` drives the Windows branch on a POSIX runner against a recording socket rather than reading the source for it - source assertions here let the option be set after the bind, at the wrong level, on the wrong socket or with a value of 0, all of which pass a check that only looks for the name. `test_a_busy_port_is_reported_before_the_browser_opens` is the only test that reaches the flow itself, and it patches the name the flow constructs; patch `HTTPServer` there instead and it guards nothing while still passing
- **The token file is the only copy of the tokens, but for a grant whose save failed.** `_refresh_token` reads it on every call, under `_token_lock`, and keeps nothing else between calls, because `bosch-flow-mcp auth` replaces it from another process while the server runs and `current_client_id` already routes by what the file says. Held in memory, the old token stays in use until a restart while routing follows the new client, so requests carry one client's token to the other client's host. **`_save_json` replaces a file in one step**: it writes a temp file beside the real file (a symlink is followed), created 0600 by `mkstemp`, syncs it, and `os.replace`s it over the old one, so on POSIX a reader sees the old file or the new one, and a failed save leaves the old one in place. `_exchange_code` reports a save that fails by its type, like every other failure there. On Windows a replace refused because another process has the file open is retried a few times with a short backoff, since every server sharing the file opens it on each request; elsewhere the refusal is a real permission fault and is raised at once. Pinned by `TestTheTokenFileIsReplacedInOneStep`. The lock is held across the refresh request, so a slow one holds every token request in the process for as long as the request takes. After a refresh the file is read again: if its token is still valid and its `expiry` later than the call started from, another writer saved it during the request, so it is used and nothing is saved, whichever client it belongs to. A starting access token that cannot be sent is refreshed whatever its expiry says, so that expiry is no baseline and counts as 0 (`test_a_grant_saved_while_an_unusable_access_token_was_refreshed_wins`). `_usable` is what decides; the comparison guards a clock that steps back during the request, which would otherwise make the untouched file look new. Otherwise the refresh is saved, since the refresh token just issued is known to be live and another copy's usually is not, and that includes over a file that cannot be read, which is gone or corrupt rather than part-way through a save. **A refusal judges the refresh token sent and nothing else**: if the file now holds one other than that, or than the one a held grant replaced, its token is used when valid and otherwise the refusal is a `RefreshNetworkError`, so the next call refreshes from the file; an unreadable file is a `RefreshNetworkError` too, and drops a held grant, since the held grant was the token refused, so the next call's read of the file decides; otherwise a file still holding either of those is a `TokenRefused`, whatever else in it changed. **A grant whose save fails is held in `_unsaved`**, because the file's refresh token may already be spent: it is used, and the save retried, on each call while the file still holds the refresh token it held when the save failed, or cannot be read, and dropped as soon as the file holds any other refresh token or the held grant is itself refused. It is the one copy kept between calls, keyed to that refresh token rather than to the whole file, and a failed save is logged once, when a grant starts being held, not on each retry. A missing file counts as unreadable, so a held grant's next save recreates a token file deleted meanwhile. `api.get` answers a 401 on a data request by retrying, which reads the file again; it never forces a refresh. Pinned by `TestTheTokenFileIsTheOnlyCopy` in `tests/test_auth.py`, whose rewrite keeps the file's length and mtime so a cache keyed on either fails it, and by `test_a_rejected_token_is_retried_with_the_token_file_as_it_is_now` in `tests/test_api.py`. **What this does not close**: something between this server and Bosch that invents a refresh token in a 200 has it saved as if Bosch issued it, which replaces a live one and ends in the next refresh being refused, the accepted price of never dropping one Bosch did issue. The rest are all across processes, which the lock does not reach: a writer that writes in place, such as a file-sync client or a release of this package up to 0.7.0, can expose a half-written file, which the first read in a call reports as a refusal, against the classification rule below, and which a refresh saves over; a write landing between the second read and the save is overwritten; of two processes refreshing at once, the loser is refused if the winner's save has not reached it, which across hosts includes the file-sync delay; a grant held after a failed save is lost if the process exits before a save succeeds, after which only `auth` repairs the file; while one process holds a grant, another reading the file finds the spent refresh token and is refused, until the holder's save succeeds on its next call; while a grant is held, an older copy put in place by another writer, such as a backup restore or a file-sync client, holds a different refresh token, so the held grant is dropped and the next refresh is refused; routing reads only the file, so while a grant is held over an unreadable one it routes by the configured client, whichever client the held grant belongs to; and on Windows, a process holding the token file open for longer than the retries, such as a file-sync client or a virus scanner, still fails the save: the server holds the grant until one succeeds, while `auth` ends in an error after the authorisation code is spent. **Replacing the file rather than writing into it has consequences for deployment**: a save needs write access to the config directory, not only to the file, and without it the server holds each refreshed grant only until it restarts, after which the file's spent refresh token means authorising again; the new file belongs to whichever user saved it, so `auth` and the server must run as the same user; a token file bind-mounted into a container on its own, rather than in its directory, cannot be renamed over, so every save fails; a hard link to the file keeps the old contents; a process killed between the write and the rename, or a cleanup that fails, leaves its temp file, 0600 and holding the token, which nothing removes; a symlink is followed, so anyone who can write the config directory can point the token file at another file the user owns and have the next save replace it, which is no wider than the same access already allows; and the directory is not synced after the rename, so a crash just after a save can bring back the old file, whose refresh token may already be spent. A sign-in written on a host whose clock runs behind by more than an access token's lifetime less the buffer looks expired here and is saved over. A sign-in saved with an expiry of 0 during a refresh is not a later grant, so the refresh saves over it, and an access-only sign-in with a lifetime inside the buffer prints success and the next call is refused (`TestResiduesThatStayOpen` in `tests/test_token_replies.py`). Routing is decided once per `run_sync` while the token is read per request, so a client switch landing mid-sync sends the rest of that sync's requests with the new token to the old host
- **API**: `api.py` - GET wrapper with thread-safe token refresh (5-min expiry buffer) and typed exceptions: `BoschAuthError`, `BoschRateLimitError`, `BoschAPIError`, `BoschForbiddenError`. **Three are siblings off `Exception`; `BoschForbiddenError` is the one subclass, of `BoschAPIError`.** So `except BoschAPIError` catches a 403 but not a 429
- **Failure classification**: `refresh_token` is a boundary over `_refresh_token` and raises exactly two types. `TokenRefused` only where the server or the credential files judged the credentials unusable; `RefreshNetworkError` for everything else, via a catch-all, so an unanticipated failure lands there by construction rather than by listing exception types. **Never widen `TokenRefused` to a condition that can clear on its own** (a rate limit, a 403 from bot protection, an unreadable response) **or to a 200 with no usable token**, which says nothing about the credentials: re-authorising rewrites the token file and spends a refresh token that was still working. A token that is not RFC 6749's token syntax (printable ASCII, not only spaces) counts as none, in an answer and in the file, because saved or sent it leads to "run auth" with the credentials never judged. So a stored access token of that kind is refreshed rather than sent, and a stored refresh token of that kind is never sent. `test_every_character_the_rule_allows_is_token_text` pins each character class the rule allows, and the `_TOKEN_TEXT` cases and `test_a_sign_in_of_valid_token_text_is_saved` carry such text through a save and a send. A stored expiry that is not a finite number counts as expired, so a file holding an infinite one refreshes. An answer saves only `access_token`, `refresh_token`, `expiry` and `client_id`, each checked first, because a field copied unchecked can be anything JSON holds. A body nested too deeply to parse raises `RecursionError`, not `ValueError`, so `_load_json` and the refresh handle it as unreadable. `api.get` has no parse handler, so there it reaches the `run_sync` catch-all and the tool gate like any other bad body. Pinned by `tests/test_token_replies.py`. **With no usable access token a 200 judges nothing**: it is a `RefreshNetworkError`. **A usable refresh token in that answer is never dropped**, because the refresh token is treated as rotating and the one sent may be spent: it is saved with an empty access token and an expiry of 0, or held if the save fails, and the next call refreshes from it. A later usable grant written during the request wins here as it does over a complete answer. With no usable refresh token either, nothing is saved, a held grant stays held, and the next call asks again. A refresh token of that kind beside a good access token counts as omitted, so the stored one is kept. A file with no `access_token` key is still refused before any refresh; a blank value is refreshed, since that is how a delivered refresh token is saved. **A lifetime that is not a finite positive number counts as already expired**, in a refresh and in `_exchange_code`: the tokens are saved with an expiry of 0 and the next call refreshes, since raising there loses a good grant and an infinite lifetime never refreshes. So a text or null `expires_in` means every call refreshes for as long as the answers stay like that. An absent one keeps the default. So does `_exchange_code` when the lifetime comes to an expiry of 0 with nothing to refresh from, since that access token would never be used. **Not closed**: a huge finite lifetime such as `1e300` is accepted and never refreshes, because a cap would be an invented number (`test_a_usable_lifetime_sets_the_expiry`). Pinned by `test_a_lifetime_that_is_not_a_finite_positive_number_means_already_expired`, `test_a_lifetime_that_cannot_be_used_saves_the_sign_in_as_already_expired` and `test_a_sign_in_with_nothing_to_refresh_from_keeps_a_usable_expiry`, and by `TestTheRefreshBoundary` and `TestRefusalsAndNetworkConditions` in `tests/test_auth.py`, and in `TestTheTokenFileIsTheOnlyCopy` by `test_a_refresh_token_delivered_with_no_usable_access_token_is_kept`, `test_a_refresh_token_delivered_with_no_access_token_is_held_if_the_save_fails`, `test_a_refresh_token_delivered_to_a_held_grant_replaces_it`, `test_a_later_grant_wins_over_a_refresh_token_delivered_alone`, `test_a_grant_with_no_usable_refresh_token_keeps_the_stored_one` and `test_a_200_with_no_usable_token_leaves_a_held_grant_held`, the first three against a token endpoint that enforces rotation
- **Client routing**: `current_client_id` and `token_is_euda` are called outside any handler and must never raise. They fall back to the **configured** client, not the hardcoded one - a EUDA user with a half-written token file would otherwise route as non-EUDA and be told to register a client they already have. `_get_client_id` carries its own guard for that promise; `_is_euda` deliberately has none that falls back, and raises `TokenRefused` with its own text instead, because its only caller is the interactive auth command where a malformed config should stop the user rather than send them through a browser login that yields the wrong client. `cli.py` prints that text in one line. A `client_id` that is not text, or is blank text, names no client in `_named_client`, so routing and a refresh agree on it. In a config, a non-null value that is not text is malformed and stops `_is_euda`, whatever its truthiness; a null, empty or blank one means no EUDA client is configured, so `auth` runs the mobile flow. Pinned by `TestTheFallbackKeepsTheConfiguredClient`, `TestTheRoutingHelpersNeverRaise`, `TestAClientThatIsNotNamed` and `test_a_refresh_with_no_client_in_the_file_sends_and_saves_the_configured_one`
- **Sync**: `tools/sync_tools.py` - routes each data type by the token's client. Standard mobile sign-in reads bikes/batteries/components/firmware/SoC; `service`/`software_updates`/`capacity` need the EUDA client and otherwise report `unavailable` (not a silent empty). **On a EUDA token with no bikes cached, the bike list decides what 0 records means.** `service` and `software_updates` ask per bike, so `run_sync` fetches the list first, inside the type's `try`, and `batteries` fetches it itself. Otherwise they find nothing to ask about and settle as `ok` with 0 records until the next UTC day. `components` and `capacity` take bike ids from the registrations, so a failed list costs them nothing while they store rows, and `run_sync` fetches it only once they have found nothing. A failure is that type's own unsettled row, so the next read retries. A 200 with no bikes (an empty body, `[]`, `{"bikes": []}` or a wrapped empty list) reports `empty`/`euda_empty` with remedy text. Any other answer from the list, a 404 or an object that holds no list, is a `BoschAPIError` from `_sync_bikes`, because that remedy tells the user to delete their config. `api.get` returns None for a 404 and `{}` for an empty body, which is what tells them apart. With bikes cached no extra request is made, and a mobile sign-in still reads those answers as no bikes. An answer holding no bike list whose `error` or `errors` is set is no bike list, so such an error envelope is not stored as a bike even with an `id`; one carrying an `id` and no error field still is, since nothing tells it from a single bike. **A bike list that cannot be read is a `BoschAPIError` on either sign-in**: a `bikes` or `data` value that is not a list where no other value holds bikes, or entries none of which carries an `id` or `bikeId` in text that is not blank. Entries that cannot be read beside ones that can are skipped. A run requests the list at most once per type, and each of those is three requests on a 401, which `api.get` retries. Pinned by `test_a_failed_bike_list_is_each_types_own_unsettled_failure`, `test_a_failed_bike_list_does_not_stop_components_the_registrations_answer`, `test_a_failed_bike_list_is_the_failure_when_nothing_else_answers`, `test_a_bike_list_answer_that_is_not_a_list_is_a_failure_on_a_euda_token`, `test_a_bike_list_that_cannot_be_read_stays_an_error`, `test_a_bike_list_that_cannot_be_read_is_no_type_s_non_eu_trap`, `test_an_error_answer_carrying_an_id_is_not_stored_as_a_bike`, `test_a_standard_sign_in_still_reads_those_answers_as_no_bikes`, `test_a_bike_list_with_no_bikes_is_the_trap_however_it_is_shaped`, `test_a_read_alone_retries_after_a_failed_bike_list`, `test_a_cached_bike_means_no_bike_list_request` and `test_a_standard_sign_in_fetches_the_bike_list_once_and_stays_ok` in `tests/test_routing.py`. **A `sync_log` row that cannot be written ends nothing**: a type that finishes has committed its data before its row, so a locked database leaves that type's result as it stands and the remaining types run. After a failure part-way through a type, an earlier bike's uncommitted snapshot is persisted by the failure row's commit, or rolled back if that row cannot be written (`test_a_failure_part_way_through_a_type_keeps_what_it_saved_only_with_its_row`). A refused commit leaves the write lock held, so the write is rolled back. The log shows the type's previous outcome until a later row lands, and auto-sync syncs the type again on the next read unless a settled row from earlier today is already there. Pinned by `TestASyncLogRowThatCannotBeWritten` in `tests/test_sync.py`. **`auto_sync_if_stale` suppresses every failure, opening the cache included**, so a read tool always goes on to its own query, which answers from the cache or reaches the gate (`TestAutoSyncKeepsItsFailuresToItself`). `run_sync` opens the cache outside its per-type handlers, so its callers meet a failure there: the gate for `bosch_sync`, and `cli.py` for `bosch-flow-mcp sync`
- **DB**: `db.py` - SQLite, default `bosch_flow.db` in the package root (`BOSCH_FLOW_MCP_DB_PATH` to override; `BOSCH_FLOW_MCP_CONFIG_DIR` for the config dir). `get_db` closes its connection if the schema cannot be applied, since the caller never receives it (`test_get_db_closes_the_connection_when_the_schema_cannot_be_applied`). Besides the per-domain data tables, a `sync_log` table records each sync's timestamp, data type, status, and rows added - query it when data looks stale. **A date range covers whole days**: a stored value usually holds a time, and as text it sorts after its own date. So an end bound compares `substr(column, 1, 10)`, since a plain `<=` drops every timestamp on the end date and keeps only a bare date. `date(?, '+1 day')` is another tempting form, and it answers nothing for `9999-12-31`, which `parse_date` accepts. `date(column)` is the third, and it moves a stamp carrying an offset to its UTC date. `TestADateRangeCoversWholeDays` in `tests/test_db.py` pins every range query separately. `test_a_months_battery_history_includes_its_last_day`, `test_a_day_count_includes_today`, `test_a_single_day_of_software_updates_includes_that_day` and `test_battery_trends_include_the_end_date` pin the tools. **A missing start counts back from the end date**, in `parse_date`, and stops at the first date `date` can hold. The tools documented as covering all records pass `EARLIEST_DATE` instead, so an end date alone means everything up to it. The `*_with_only_an_end_date_*` tests in `tests/test_tools.py` and `tests/test_analysis.py` pin each tool. **`parse_date` refuses a start after the end with `InvalidDateError`, comparing the resolved dates**, since the empty answer reads as no data. No end date precedes `EARLIEST_DATE`, so an end date alone is never refused over a start the caller did not send. A start after today with no end is inverted too, and the refusal calls that end today. A tool parses its dates before auto-sync, so a refused date costs no sync. Pinned by `TestAnInvertedRange` in `tests/test_helpers.py`, and for each tool through the server's registry by `test_every_date_tool_refuses_an_inverted_range`, `test_every_date_tool_refuses_a_start_after_today_with_no_end`, `test_an_end_date_alone_is_never_refused` and `test_a_refused_date_costs_no_sync` in `tests/test_tools.py`. `bosch_get_batteries` with `latest_only=True` reads no dates, so it refuses nothing, and nothing pins that. **The comparison reads the date written in the stored value.** A battery snapshot's date is UTC, while `parse_date`'s default end date and its `Nd` count from the host's local date. So west of Greenwich an evening's snapshot carries tomorrow's date and sits outside a default range until the local date catches up. East of Greenwich, just after local midnight, a snapshot's written date is still yesterday, so `0d` misses it. "Today" is the host's date and not the caller's, so a container on UTC can refuse a caller's own today east of Greenwich. Nothing pins these residues
- **Tools**: `tools/` - `@mcp.tool` definitions grouped by domain (bike, battery, component, service, analysis, activity, sync). Cached `get_*` tools auto-sync if stale; `bosch_get_soc`, `bosch_get_activities`, and `bosch_get_activity_detail` are live reads

## Key invariants

- **Capacity sync depends on components** - it needs part + serial numbers, so with no battery component cached `_sync_capacity` fetches components itself, inside the type's `try`. A battery is any type that casefolds to `battery` or `batteries`, read through `db.component_types`, because Bosch owns these values, and one battery held under two spellings is asked about once. A failed fetch is `capacity`'s own unsettled row, so the next read retries. A fetch that answers with no battery stays `ok` with 0 records and settles. That is true of a bike whose registrations list its parts. It is not true when a 404 or an unrecognised object left them empty, and nothing tells those apart (`test_a_registrations_answer_that_holds_nothing_reads_the_same`). `capacity` repeats the registrations request whenever no battery is cached by the time it runs: `components` failed or found none earlier in the run, or runs after it. Each of those is three requests on a 401. `components` still runs first in the dispatch to avoid that. A bare object from the capacity tester, or one held under `data`, counts as one test only if it carries a date, since an envelope holding no test would otherwise be stored as one (`test_a_tester_answer_holding_no_test_stores_nothing`). A test inside a list is stored as it comes, and an entry that is not an object is skipped. **An undated test is stored once**: the table's UNIQUE key treats NULL dates as distinct, so `db.save_capacity_test` skips an undated row whose part, serial and JSON are already stored (`test_an_undated_test_in_a_list_is_stored_once`, `test_undated_tests_that_differ_or_belong_to_another_battery_are_all_kept`). Undated rows stored by earlier releases stay. Pinned by `test_a_failed_components_fetch_is_capacitys_own_unsettled_failure`, `test_a_first_capacity_read_on_an_empty_cache_fetches_what_it_needs`, `test_a_good_fetch_with_no_battery_component_stays_ok_and_settles`, `test_a_cached_battery_means_no_components_request`, `test_one_battery_under_two_spellings_is_asked_about_once` and `test_a_full_run_on_an_empty_cache_counts_its_requests` in `tests/test_routing.py`
- **Route by token client, never call both hosts blindly** - the sync layer picks the host from the authenticated client_id
- **Nothing an exception carries reaches a stored note: not the response body, and not the request path.** `run_sync` writes its note into `sync_log`, and `helpers.empty_data_note` reads that row back and returns it as `note` on every empty `bosch_get_*` result, so anything stored is repeated to the model indefinitely. The three live reads are not stored and do return `str(e)` for a `BoschAPIError`, so their tool result can name the request path. The capacity request path carries a part number and a battery serial, which is why the messages are the fixed `AUTH_FAILED_MSG` / `RATE_LIMITED_MSG` / `API_FAILED_MSG` plus at most an exception type name. `api.get` raises a status code and a path, never the body. Pinned by `TestNoRequestPathReachesTheSyncLogOrAModel` and `test_the_api_layer_never_puts_a_response_body_in_its_message` in `tests/test_sync.py`
- **The same rule governs what `bosch-flow-mcp auth` prints, and that is a terminal rather than a stored note.** `_exchange_code` reports a refused exchange as its status code, a transport failure as `type(e).__name__`, an unreadable body and a response carrying no access token as fixed text. An access token that is not RFC 6749's token syntax (printable ASCII, not only spaces) counts as none, and nothing is saved, since saved it reports success and every later call is refused. A refresh token of that kind counts as omitted, so an empty one is saved and `auth` says so. The stored one is never kept: the same client is not the same account, and another account's refresh token beside this sign-in's access token silently serves that account's data once the access token expires. Pinned by `test_a_sign_in_with_no_usable_refresh_token_saves_none`. None may carry the server's own words: an error body can name an account, `str(e)` carries text the peer influences (a TLS name mismatch echoes an identity string out of the handshake; measured, a refused connection and a DNS failure name no path, so do not justify this one by paths), and the no-access-token branch is reached by exactly the response shape that carries a `refresh_token`, so printing the dict to explain the failure puts a live credential on screen. **It also has to reach its own message**, which is why the `OSError`, `HTTPException`, `ValueError`, `RecursionError` and `isinstance` guards are there: `urlopen` wraps only connect-phase failures, and a read timeout, a malformed HTTP response, a non-JSON body, a body nested too deeply to parse or a JSON scalar otherwise escapes as a traceback naming this install's absolute paths. Pinned by `TestTheCodeExchangeReportsNoResponseContent` in `tests/test_auth.py`, which **asserts the whole message rather than the absence of a secret**, since appending the HTTP reason phrase, the response headers or an `error_description` passes any "is this string absent" check. It asserts all three channels: stdout, stderr and `caplog`. stdout because every other print here goes there, so a bare `print` is the likeliest reintroduction; `caplog` because a `logger` call is invisible to `capsys` under pytest and lands on the terminal in production
- **A failure that stops `auth`, or stops `sync` before any type runs, ends in one line on stderr and exit 1, not a traceback, which names this install's absolute paths.** `cli.py` catches around both commands. `TokenRefused` prints as it is: on this route only `_is_euda` raises it, so a malformed config stops the user, and its text names a file by its base name and does not send them back to `auth`. An `OSError` prints only its type, because its text names a path. A `sqlite3.Error` prints its text, which says what is wrong: `database is locked`, `file is not a database` and `unable to open database file` are the ones measured, and none names a path. The prompt in `_setup_mobile_auth` reports its own failures in fixed text: no input left, a closed stdin, bytes that will not decode, and a paste `urlparse` refuses. The EUDA callback answers a request whose URL `urlparse` refuses with a 400, so `auth` ends in its own `no auth code received` rather than `socketserver`'s traceback (`test_a_callback_url_that_will_not_parse_is_refused_without_a_traceback`). An interrupt prints one line and exits 130. Anything else keeps its traceback, because it is a bug, so `Exception`, `ValueError` and `RuntimeError` are deliberately not caught here (`test_an_unanticipated_failure_is_not_reported_as_an_ordinary_one`). **A type that fails during `sync` is not one of these**: `run_sync` reports it per type, `cli.py` prints it on stdout, and the command exits 0, deliberately (`test_a_type_that_fails_during_sync_prints_on_stdout_and_exits_0`). Pinned by `TestAFailedCommandEndsInOneLine` in `tests/test_cli.py`, which compares all of stderr through real `main()` and asserts nothing reached `caplog`
- **`require_auth` is the backstop every tool has.** `BoschRateLimitError` is a sibling of `BoschAPIError` rather than a kind of it, so `except BoschAPIError` does not catch a 429. The three live reads catch `BoschAuthError`, `BoschForbiddenError` and `BoschAPIError` themselves and keep their own wording; the cached tools catch nothing. No live read catches `BoschRateLimitError`, so a 429 from one reaches the gate. Without the gate's own `try` it would reach the model as `mcp`'s masked `Error executing tool <name>`, with nothing saying it is a rate limit or that a retry will work. `run_sync` needs its own handlers for the same reason, including a trailing catch-all. `InvalidDateError` passes through with its message intact - it is the server's own text and it tells the model how to retry, which is why it is a distinct type rather than a bare `ValueError` a JSON decode could also raise. Pinned by `TestTheAuthGate` in `tests/test_helpers.py`, which also pins the refusal when there are no credentials, and by `test_every_tool_is_gated`. **Because the gate returns a result rather than re-raising, `mcp` 2.1's masking does not apply to this server** - that release keeps only a `ToolError`'s text and replaces every other exception's with `Error executing tool <name>`, which costs a server whose tools *raise*. Measured over a real stdio handshake on 2.1.1: a bad date still arrives as `Invalid date '...'. Use YYYY-MM-DD...`. So do not add a `ToolError` conversion here; it would convert what this gate has already turned into an answer. What keeps that true is `test_an_unanticipated_failure_becomes_a_tool_result` and `test_a_bad_date_keeps_its_message_so_the_model_can_retry`, so a change that let an exception escape the gate would fail those before it reached a client
  - **The one refusal the gate never sees is a schema refusal**, because it happens above every decorator: an argument constrained by its annotation is rejected before the tool body is entered, and `mcp` raises that as a `ToolError`, which is the one type whose text 2.1 keeps. Measured over a real stdio handshake on 2.1.1: it reaches the client as a result carrying `isError: true` and the whole validation message, `Input should be 'weekly', 'monthly' or 'quarterly'`. Both halves of that matter and they have different causes. Sitting above the gate is why the gate never sees it. The `ToolError` type is why the message survives, so do not read this as a general licence for anything raised above the gate, and it is not a reason to add a `ToolError` conversion inside one
- **`bosch_battery_trends`' `period` is constrained in the annotation, so the server refuses before any body runs.** The class this closes is a wrong answer rather than bad input: a lookup that falls back to a default period would return monthly buckets under whatever label was sent, because the response echoes `period` back. Real figures, no error, nothing empty. `TrendPeriod` is unpacked from `_PERIOD_KEY_FNS` (`Literal[*_PERIOD_KEY_FNS]`), so the schema offers exactly the periods there is a key function for. **Two residues stay open and both relabel exactly as quietly**: two dispatch entries pointing at the same key function, and the call site ignoring the dispatch and calling a key function by name. Neither is visible from the echoed label, which is why `test_every_accepted_period_still_answers_under_its_own_label` asserts the shape of every bucket key rather than only the label, and `test_a_period_separates_dates_that_belong_to_different_buckets` covers the third case, a key function that collapses its own family. The docstring's `Options:` list and its `(default)` marker are two more copies, read back by `test_the_documented_periods_are_the_accepted_ones` and `test_the_default_is_a_value_the_schema_accepts`. All of it in `tests/test_argument_validation.py`, whose calls go through `mcp.call_tool`, the only layer that applies the schema, so a test calling the function directly passes whether the constraint is there or not.
- **`bosch_get_components`' `component_type` is checked against the cache, because Bosch defines those values and this server does not.** An annotation is the wrong mechanism for an open set: a `Literal` would refuse a component type a future bike registers. So the filter is resolved against the types the `components` table holds, ignoring case, and a value none of them match is refused with those types named. **A type held under more than one spelling answers under all of them.** A bike's profile keys and its registrations describe the same part, so `battery` and `Battery` can both be stored, and resolving to whichever sorts first drops the other's rows, which is a confident partial answer in place of a correct one. The fold is `casefold` on both sides rather than SQL `COLLATE NOCASE`, which is ASCII-only: mixing the two lets a value the membership test accepted come back empty from the query. **An empty cache refuses nothing**, because with no rows there is nothing to name in a refusal; that reply stays thin, since a sync recording `ok` with nothing to store leaves `empty_data_note` silent as well. And **the vocabulary is account-wide, never per bike**: a type one bike does not carry is a true empty result, so scoping the known set by `bike_id` would report a real component type as unknown. Each of those is pinned in `tests/test_component_type_filter.py`, the fold by a stored type outside ASCII asked in another case: that is the only input that tells the two folds apart, and without it a rewrite moving the comparison into SQL passes the whole suite while answering nothing. The thin reply is pinned by asserting the absence of a note, so an explanation cannot be added to that path while this says there is none. `bike_id` is not checked here at all, so an id no bike has is still answered with an empty list, where `bosch_get_bike` refuses one; nothing pins that, it is a residue

## Seams the suite does not cross

Nothing in the suite fails if these break, so check them by execution when they change.

- **The pre-commit guard.** `scripts/check-no-data.sh` is not run by any test or by CI. To check a change to it, work in a throwaway clone: stage one probe per class it should refuse, plus one it should pass, using `git add -f` for gitignored paths, and compare the script's exit code with what you expect.

## Test conventions

Tests are fully offline - no real API calls or tokens - and use temporary SQLite databases (`tmp_path` fixture), never the real DB. See [CONTRIBUTING.md](CONTRIBUTING.md) for how to run them.

**The autouse `_no_network` fixture in `tests/conftest.py` is what holds "offline".** It replaces `urllib.request.urlopen`, the only call `src/` makes a request through, so a test that reaches for it fails, and one that means to serve a request patches `urlopen` itself. The refusal is `pytest.fail` rather than `assert` because `refresh_token` and `run_sync` end in `except Exception`, which absorbs an `AssertionError`; `Failed` derives from `BaseException`. A raw thread keeps `Failed` to itself and pytest reports that only as a warning, so `pyproject.toml` turns that warning into an error. Pinned by `tests/test_harness.py`, since deleting the fixture fails nothing else. It sees `urlopen` alone: a route through `http.client` or a socket would pass it.
